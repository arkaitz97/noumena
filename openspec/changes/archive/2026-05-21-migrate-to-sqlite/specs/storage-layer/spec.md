## ADDED Requirements

### Requirement: SQLite storage backend

The system SHALL use SQLite as its sole storage backend, replacing PostgreSQL. All data operations SHALL function identically from the application's perspective.

#### Scenario: Application starts with SQLite database
- **WHEN** the application starts with a valid `DATABASE_PATH` environment variable
- **THEN** the system connects to the SQLite database at that path and applies the schema if tables do not exist

#### Scenario: Schema is idempotent
- **WHEN** the schema SQL is executed against an existing database
- **THEN** no errors occur and all existing data is preserved

### Requirement: UUID generation in Go

The system SHALL generate UUIDs in Go using `github.com/google/uuid` before inserting rows, replacing PostgreSQL's `gen_random_uuid()` defaults.

#### Scenario: New row receives UUID
- **WHEN** a new user is created
- **THEN** the user record has a valid UUID primary key generated by the application

### Requirement: JSON data storage

The system SHALL store JSON data (actionable insights, digest content, export filters, audit details) as TEXT columns with SQLite JSON functions for querying.

#### Scenario: Comment stores actionable insights as JSON
- **WHEN** a comment is processed by the LLM
- **THEN** the `actionable_insights` column contains valid JSON queryable via `json_extract()`

#### Scenario: JSON array of comment IDs
- **WHEN** an LLM processing job is created
- **THEN** the `comment_ids` column contains a JSON array of UUID strings

### Requirement: Full-text search via FTS5

The system SHALL provide full-text search on comment bodies using SQLite FTS5, replacing PostgreSQL's `to_tsvector()`/`plainto_tsquery()`.

#### Scenario: Search returns matching comments
- **WHEN** a user searches for a term in comments
- **THEN** comments containing the term are returned ranked by relevance

### Requirement: Job queue atomic claiming

The system SHALL claim jobs from queues (ingestion, LLM processing, exports, deletions) atomically using `UPDATE ... WHERE` with `RETURNING`, replacing `FOR UPDATE SKIP LOCKED`.

#### Scenario: Single worker claims pending job
- **WHEN** a worker requests the next pending ingestion job
- **THEN** exactly one job transitions from `pending` to `processing` and is returned to the worker

#### Scenario: Concurrent workers do not claim same job
- **WHEN** two workers simultaneously request the next pending job
- **THEN** each worker receives a different job (or one receives none)

### Requirement: Ingestion serialization without advisory locks

The system SHALL serialize per-channel ingestion using SQLite's native write serialization, replacing PostgreSQL advisory locks.

#### Scenario: Only one ingestion runs per channel
- **WHEN** an ingestion job starts for a channel
- **THEN** no other ingestion job for the same channel can start until the first completes

### Requirement: Upsert operations

The system SHALL support upsert operations using `INSERT ... ON CONFLICT DO UPDATE`, maintaining identical behavior to PostgreSQL's `ON CONFLICT`.

#### Scenario: Insert new comment
- **WHEN** a comment with a new `platform_comment_id` is upserted
- **THEN** the comment is inserted

#### Scenario: Update existing comment
- **WHEN** a comment with an existing `platform_comment_id` is upserted
- **THEN** the existing comment is updated with new values

### Requirement: CHECK constraints

The system SHALL enforce CHECK constraints on status fields, billing intervals, and role fields, matching PostgreSQL behavior.

#### Scenario: Invalid status rejected
- **WHEN** an insert attempts to use an invalid status value
- **THEN** the database rejects the insert with a constraint error

### Requirement: Partial indexes

The system SHALL create partial indexes with `WHERE` clauses for query optimization, matching PostgreSQL partial index behavior.

#### Scenario: Partial index filters correctly
- **WHEN** a query targets only pending ingestion jobs
- **THEN** the partial index `WHERE status = 'pending'` is used

### Requirement: Recursive CTEs for comment threads

The system SHALL traverse comment reply trees using recursive CTEs, maintaining identical behavior to PostgreSQL.

#### Scenario: Get full comment thread
- **WHEN** a user requests a comment thread
- **THEN** all replies are returned in hierarchy order via recursive CTE

### Requirement: Window function aggregation

The system SHALL compute aggregated insight counts using window functions or equivalent, replacing the materialized view.

#### Scenario: Insight counts computed
- **WHEN** the actionable insights aggregation query runs
- **THEN** per-topic insight type counts are returned with window function results

### Requirement: Aggregate FILTER replacement

The system SHALL compute conditional aggregates using `SUM(CASE WHEN ...)` patterns, replacing PostgreSQL's `FILTER (WHERE ...)` syntax.

#### Scenario: Toxicity shield metrics
- **WHEN** toxicity metrics are queried
- **THEN** conditional counts are computed using CASE expressions

### Requirement: Rate limiting with upsert

The system SHALL implement sliding window rate limiting using upsert on rate limit buckets, maintaining identical behavior.

#### Scenario: Rate limit counter increments
- **WHEN** a request is made within an existing window
- **THEN** the counter increments via upsert

#### Scenario: New window created
- **WHEN** a request is made after window expiry
- **THEN** a new rate limit bucket is created

### Requirement: Test harness with in-memory SQLite

The system SHALL run all database tests against in-memory SQLite databases without Docker or external services.

#### Scenario: Tests run without Docker
- **WHEN** `go test ./...` is executed
- **THEN** all database tests pass using in-memory SQLite databases

#### Scenario: Test isolation
- **WHEN** multiple tests run in parallel
- **THEN** each test has its own isolated in-memory database

### Requirement: Connection configuration via DATABASE_PATH

The system SHALL read the SQLite database path from the `DATABASE_PATH` environment variable, replacing `DATABASE_URL`.

#### Scenario: Valid database path
- **WHEN** `DATABASE_PATH` is set to a valid file path
- **THEN** the application connects to that SQLite database

#### Scenario: Default database path
- **WHEN** `DATABASE_PATH` is not set
- **THEN** the application uses a default path of `./noumena.db`

### Requirement: WAL mode and busy timeout

The system SHALL enable `PRAGMA journal_mode=WAL` and `PRAGMA busy_timeout=5000` on database connection for concurrent read performance and write contention handling.

#### Scenario: WAL mode enabled
- **WHEN** the database connection is established
- **THEN** WAL journal mode is active

#### Scenario: Busy timeout handles contention
- **WHEN** multiple goroutines attempt writes simultaneously
- **THEN** waiting goroutines retry for up to 5 seconds before failing
